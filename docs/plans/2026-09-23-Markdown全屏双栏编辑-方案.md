# Markdown 全屏双栏编辑方案

## 1. 目标与当前约束

用户希望在编辑 Markdown 时，从当前编辑页面切换到占满应用视口的双栏工作区：左侧持续编辑，右侧实时渲染。切换布局不应丢失正在编辑的正文、标题、摘要、分类和标签，保存仍使用原页面的提交逻辑。

当前代码核对结果：

- `/notes/:id/edit` 和 `/notes/new` 均由 `apps/web/src/views/NoteEditor.tsx` 渲染，处于 `AppLayout` 的顶栏和侧栏内。
- 桌面端 `.editor-layout` 已有两列，但左列是元数据表单，右列 `MarkdownEditorPanel` 是“编辑/预览”互斥模式，并非 Markdown 源码与渲染结果同时可见。
- `MarkdownEditorPanel` 被 `NoteEditor`、`SolutionEditor`、`MiscellanyEditor`、`ModelResponseEditor` 和 `PromptEditor` 复用；其源码编辑使用 `PromptMonacoEditor`，预览走 `useMarkdown` → `MarkdownContent`，包含现有引用展示能力。
- 页面保存校验和请求在各自的 Editor view 中；学习笔记保存校验标题、正文、至少一个标签，成功后跳转详情页。
- `AppLayout` 的顶栏、侧栏和内容区含固定尺寸与最小宽度；全屏工作区需要独立覆盖这些布局约束。当前整体应用并未完善窄屏布局，全屏模式需自行提供窄屏退化方式。

这里的“全屏”定义为**占满浏览器内容视口的沉浸式工作区**，不触发浏览器原生 Fullscreen API。切换不改 URL、不重新取数、不自动保存。

## 2. 交互设计

### 入口与视觉层级

- 在 `PageHead` 的“保存”左侧放“全屏双栏”次要按钮。它改变整个编辑页面的布局，并要保留保存入口，因此放在页面级操作区比放在正文 `editor-head` 更符合操作范围。
- 默认页面维持现状。进入全屏后，以固定视口工作区覆盖应用顶栏和侧栏，不出现另一套导航。
- 全屏顶部使用紧凑工具栏：返回普通布局、笔记标题、元数据入口、保存状态与保存按钮。标题输入留在“元数据”面板中，工具栏显示其即时摘要。
- 主工作区左侧为 Monaco 编辑器，右侧复用当前 Markdown 渲染组件；两列独立滚动，初始各占一半，允许拖动中间分隔条调整宽度，边界建议为 35% 至 70%。
- 元数据从工作区顶部按钮打开侧面板，继续编辑标题、摘要、分类、标签；使用原表单状态，不建第二份草稿。

### 状态与行为

- 正文输入立即更新页面草稿，右栏随输入更新；用 React 18 的 `useDeferredValue` 或等效调度避免长文档渲染阻塞 Monaco。预览仍通过现有 `useMarkdown` 和 `MarkdownContent`，不引入第二套解析器。
- 空正文显示预览空状态。渲染失败时保留编辑能力，在预览列内显示错误和重试入口。保存沿用现有校验、Toast、请求与成功跳转；保存中按钮禁用。
- 退出全屏只切换布局，保留草稿和光标/滚动位置。优先保持同一 `PromptMonacoEditor` 实例，通过容器样式切换布局；不要在切换时重新创建编辑器。
- `Esc` 先关闭元数据面板，再退出全屏。按钮均支持键盘焦点、`aria-label`；元数据面板打开时管理焦点与滚动。
- 视口不足以容纳两列时，工作区改为“编辑 / 预览”标签切换，仍占满视口且不产生横向滚动。此行为仅针对新工作区，普通页面的现有响应式问题另行处理。
- 初版不做编辑与预览滚动同步。Markdown 中表格、代码块和图片高度不稳定，直接按滚动百分比映射会产生明显错位；如以后有需要，再基于标题锚点或源码行映射设计。

## 3. 候选方案

### A. 页面内沉浸式工作区（推荐）

**思路**：在编辑页维护布局状态，让同一份表单和 `MarkdownEditorPanel` 在普通/全屏状态间切换。全屏根容器固定覆盖视口，正文面板增设 `split` 模式，右列复用已有预览。先以学习笔记验证交互，再将页面级接入复用到其余 Markdown 编辑页。

- 优点：URL、表单状态和保存流程稳定；可以保留 Monaco 实例；无新路由与依赖；既能覆盖整个应用界面，也能明确处理元数据。
- 缺点：需要认真处理固定层级、滚动锁定、焦点和当前 `.app-shell` 最小宽度；各资源页接入全屏工具栏时仍需传入对应保存动作和标题。
- 适用：当前 monorepo 与共享编辑面板结构，且希望无缝切换。

### B. 独立编辑工作区路由

**思路**：增加类似 `/notes/:id/edit/split` 的无侧栏路由，由独立布局承载双栏编辑。

- 优点：路由、布局、样式隔离清楚；可直接分享工作区 URL；未来若要独立编辑产品更易扩展。
- 缺点：切换路由会重新挂载页面，若草稿只在本地组件状态中，必须提升状态或持久化草稿，才能保证不丢编辑内容；五类资源都需要路由和保存状态适配，初期成本高。
- 适用：明确要求工作区有独立 URL、跨设备恢复或多文档编辑。

### C. 浏览器 Fullscreen API 加双栏组件

**思路**：点击按钮后调用 `requestFullscreen()`，再渲染双栏布局。

- 优点：浏览器工具栏也可隐藏，显示面积最大。
- 缺点：权限与浏览器行为不一致，`Esc` 会由浏览器直接退出；移动浏览器支持与焦点行为复杂；仍需实现 A 或 B 的双栏组件，不能替代应用布局设计。
- 适用：未来明确需要演示/演讲式的浏览器级全屏，可作为可选增强。

| 方案 | 实现复杂度 | 预览性能 | 维护性 | 扩展性 | 实施成本 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| A 页面内工作区 | 中 | 复用现有渲染，可调度 | 高，页面状态连续 | 可扩展到五类 Markdown 编辑页 | 中 | 无缝进入和退出 |
| B 独立路由 | 高 | 与 A 相近，切换时需重建页面 | 路由边界清楚，草稿机制更复杂 | 独立 URL 能力强 | 高 | 独立工作区产品化 |
| C 浏览器 Fullscreen API | 中高，仍须配合 A/B | 与 A/B 相同 | 受浏览器差异影响 | 浏览器级展示能力 | 中高 | 需要真正隐藏浏览器界面 |

## 4. 推荐方案与实施边界

推荐 **A：页面内沉浸式工作区**。当前需求关键是“编辑与渲染同时可见、布局占满屏幕、切换时保持草稿”。A 使用当前已存在的 Monaco、Markdown 渲染和页面提交链，接入成本与状态风险最低。入口放在 `PageHead`，全屏后另显示紧凑工具栏。

建议按以下顺序落地：

1. `MarkdownEditorPanel` 增加受控的 `split` 显示能力，但不改变其他页面的默认编辑/预览行为。让编辑器 DOM 在模式切换中保持挂载。
2. 在 `NoteEditor` 接入页面级全屏布局与元数据面板，复用现有 `form`、`handleSubmit` 和保存校验；补充工作区局部样式。
3. 验证学习笔记的新建、编辑、切换、保存、长文档与窄屏后，再将相同工作区接入 `SolutionEditor`、`MiscellanyEditor`、`ModelResponseEditor`、`PromptEditor`。各页面保持自身字段和提交逻辑，不合并业务表单。

预计涉及 `apps/web/src/views/NoteEditor.tsx`、`apps/web/src/components/markdown/MarkdownEditorPanel.tsx`、`apps/web/src/assets/main.css`；后续扩展再涉及其他四个 Editor view。无需修改 API、Prisma Schema 或路由。是否要一次覆盖五类页面，可在确认原型后确定。

## 5. 验收重点与风险

- 进入/退出全屏后，正文、元数据、Monaco 光标与滚动位置保留；普通模式原“编辑/预览”切换保持可用。
- 实时预览与详情页渲染一致，尤其是代码块、表格、Mermaid、引用来源、链接安全处理；不使用原型中的简化解析逻辑实现正式功能。
- 两列独立滚动、拖动边界稳定；960px 以下及移动宽度无横向溢出，元数据入口和保存可操作。
- 保存中、校验失败、预览空状态、预览异常与退出全屏行为明确；Toast 和确认弹窗显示在工作区上方。
- 变更后运行允许的 lint/静态检查和浏览器交互检查；本项目禁止未经同意运行构建/编译命令。
