# Markdown 外部图片白名单与管理页方案

## 1. 结论

推荐采用“**服务端持久化精确 Host 白名单 + 前端默认拒绝渲染 + 管理页原子更新**”方案，不在本阶段引入图片代理。

管理员在“图床白名单”页面维护允许加载的 HTTPS Host，例如 `cdn.example.com` 或 `images.unsplash.com`。所有 Markdown 详情、编辑器预览和批注预览从同一份策略读取；只有图片 URL 的规范化 `hostname` 与白名单精确相等时，才输出 `<img>`。未加载策略、策略请求失败或 Host 未授权时，一律不创建 `<img>`，从而不向外部站点发起图片请求。

该方案满足当前“可配置白名单”的目标，保持 Markdown 原文、导入和导出不变；删除某个 Host 后，历史 Markdown 无需改写，重新渲染时立即不再展示该 Host 的图片。图片代理、缓存和上传自有对象存储作为后续可选演进，而非本次实现前置条件。

## 2. 已核对的约束

- 当前生产渲染链为 `useMarkdown` → `MarkdownContent`；详情页、`MarkdownEditorPanel` 预览与 Markdown 批注预览均复用该链路。
- `useMarkdown` 当前同步产出 HTML，因此白名单策略应由应用级 Provider/Store 先异步加载，再作为显式解析选项传入；策略未就绪必须默认拒绝，不能先渲染再撤回。
- 后端使用 NestJS、Prisma、Swagger，统一前缀为 `/api`。全局 `AdminWriteGuard` 已保护所有非安全方法；GET 默认公开，适合向访客下发不含密钥的白名单。
- 管理侧已有 `/categories`、`/tags` 路由和左侧“管理”导航，可复用表格、输入、确认弹窗和 Toast 的交互模式。
- 现有 UI 原型的 `allowExternal` 是隔离 iframe 专用配置，不应与 Markdown 图片策略混用。

## 3. 候选方案

### 方案 A：在前端写死域名数组

- 核心思路：在 `use-markdown.ts` 中常量维护允许的 Host。
- 优点：改动最少，无接口、数据库和管理页。
- 缺点：每次调整都要发版；无法满足管理员维护需求；多环境配置容易漂移。
- 适用场景：仅临时验证或域名永久固定的内部工具。

### 方案 B：服务端白名单配置，前端直接按白名单加载图片（推荐）

- 核心思路：后端保存单例策略；前端启动时读取并默认拒绝；Markdown 解析时精确比对 HTTPS 图片 Host；管理员通过专用页面更新整份列表。
- 优点：策略可运营、立即对所有 Markdown 类型生效、无服务端抓取外部 URL 的 SSRF 面；实现和运维成本适中。
- 缺点：允许的第三方图床仍可获知访问者 IP 与访问时间；策略变更后其他已打开页面需触发重新校验或刷新。
- 适用场景：当前管理员维护 Markdown、需要允许若干可信图床的项目。

### 方案 C：白名单加后端图片代理/缓存

- 核心思路：前端只加载本项目 `/api/markdown-images/...`，服务端根据白名单拉取、校验、缓存远程图片。
- 优点：浏览器不直连第三方图床；可统一限制大小、MIME 类型、缓存、热链和 CSP 为 `img-src 'self'`。
- 缺点：必须处理 SSRF、DNS 重绑定、重定向、私网地址、响应体大小、超时、图片解码和缓存淘汰；服务端带宽与存储成本显著增加。
- 适用场景：Markdown 来源不可信、隐私要求较高，或需要稳定保留第三方图片快照。

### 方案 D：只允许上传至自有对象存储

- 核心思路：禁用外部 URL，提供受控上传并在 Markdown 中引用本域资源。
- 优点：安全边界与内容可用性最稳定，彻底消除外链追踪和远端替换风险。
- 缺点：需要上传、文件扫描、对象存储、配额、删除回收和迁移能力；不能满足直接引用既有图床图片的便利性。
- 适用场景：内容需要长期归档、合规审计或完全内部化部署。

## 4. 横向对比

| 方案 | 实现复杂度 | 访问者隐私 | 运维成本 | 策略可配置性 | SSRF 风险 | 适用性 |
| --- | --- | --- | --- | --- | --- | --- |
| A. 前端常量 | 低 | 低 | 低 | 无 | 无 | 不满足本需求 |
| B. 持久化白名单直连 | 中 | 中 | 低 | 高 | 无 | **当前推荐** |
| C. 图片代理/缓存 | 高 | 高 | 高 | 高 | 高，需专门治理 | 高安全场景 |
| D. 自有对象存储 | 高 | 高 | 中至高 | 中 | 无 | 长期内容治理 |

## 5. 推荐方案的设计

### 5.1 白名单语义

- 仅允许没有 `username/password`、没有非默认端口的 `https:` 图片 URL；不允许 `http:`、`data:`、`blob:`、`file:`、协议相对 URL、非默认端口及 URL 用户信息。
- 每项是**精确 Host**，不带协议、端口、路径、查询参数或通配符；保存时统一转为小写并由 `URL.hostname` 规范化后比较。
- 首版不支持 `*.example.com`。显式加入 `img.example.com` 比后缀匹配更不易误放行恶意子域，也便于审计。
- 拒绝 IP 字面量、`localhost`、仅内网语义的名称及格式不合法的 Host。将来确有受控内网图床需求时，应单独评审，而不是放宽公共规则。
- 白名单默认空数组，即默认拒绝。策略未加载或读取失败也默认拒绝，不能降级为允许任意外部图。
- 不校验或改写 Markdown 原文；白名单是“渲染策略”而非“内容格式限制”。这保证导入、导出和历史内容保真，管理员新增 Host 后可让既有图片生效，删除 Host 后可立即阻断后续渲染。

### 5.2 后端数据与 API 契约

新增 `MarkdownImagePolicy` 单例模型，固定 `id = 'default'`：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `String` | 单例固定值，用于 Prisma upsert |
| `allowedHosts` | `String[]` | 已规范化、去重、按字母排序的精确 HTTPS Host |
| `version` | `Int` | 乐观并发版本，避免两个管理页相互覆盖 |
| `updatedAt` | `DateTime` | 最近策略变更时间 |

新增 `markdown-image-policy` NestJS 模块、DTO、Service 与 Controller，并在 `AppModule` 注册。接口如下：

| 方法 | 路径 | 权限 | 请求 | 响应与语义 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/markdown-image-policy` | 公开 | 无 | 返回 `{ allowedHosts, version, updatedAt }`；无记录时返回空白策略，不暴露内部密钥 |
| `PUT` | `/api/markdown-image-policy` | 管理员 Cookie | `{ allowedHosts: string[], expectedVersion: number }` | 原子替换整个集合，成功返回新策略；版本过期返回 `409` |

`PUT` DTO 应限制 0 至 100 项、单项长度最多 253，并验证每一项均为可规范化的精确域名。Service 使用条件更新或事务确保 `expectedVersion` 与当前版本一致；不要采用多次 DELETE/INSERT 的部分成功写法。Controller 添加 Swagger 成功、`400`、`401`、`409` 注解；API 文档新增 `docs/api/markdown-image-policy.md` 并写入 `docs/api/README.md` 索引。

白名单 Host 列表不是凭据，允许公开读取；写入仍完全交由现有 `AdminWriteGuard`。不创建 Postman 共享资源、不发布外部文档；实施时应在本地 API 契约或集合中覆盖未认证写入、非法 Host、版本冲突和空列表。

### 5.3 前端渲染边界

新增应用级 `MarkdownImagePolicyProvider` 或 Zustand Store：

1. `AppLayout` 挂载时读取策略，维护 `loading | ready | failed` 状态、Host `Set`、版本和刷新函数。
2. `useMarkdown` 读取该状态，将允许 Host 作为显式依赖传入其纯解析入口；扩展 `UseMarkdownOptions`，使纯 `parseMarkdown` 仍可传入确定的 Host 集合并保持可测试。
3. 图片规则先解析 URL，再确认协议为 HTTPS 且 `hostname` 精确在集合内，才调用 `renderMarkdownImage`。
4. `loading`、`failed` 或未授权时返回不包含 `src` 的受限提示节点，例如“图片来源未获授权”，不能保留一个可被浏览器请求的隐藏 `<img>`。
5. 页面重新获取策略、管理页保存成功、浏览器回到前台时刷新解析依赖；策略变更导致已渲染图片失效时，React 重新渲染并移除对应 `<img>`。已完成的历史网络请求无法撤回，这是浏览器模型限制。

此策略必须覆盖 `MarkdownEditorPanel`、详情页 `MarkdownAnnotationSurface`、批注预览及其他直接调用 `useMarkdown` 的地方；不得只在单一详情页或 CSS 层隐藏图片。图片仍输出已存在的 `loading="lazy"`、转义属性和 `referrerpolicy="no-referrer"`。

### 5.4 管理页面

新增仅管理员可访问的 `/markdown-image-policy` 路由和左侧“管理 → 图床白名单”入口，使用 `Image` 图标和既有本地 UI 组件。

- 页面顶部说明精确匹配、仅 HTTPS、无通配符，以及“移除域名会使历史 Markdown 中对应图片停止展示”。
- 主区域是可扫描的 Host 表格：域名、加入顺序或更新时间、删除操作；无配置时显示明确空状态。
- 顶部输入框用于新增 Host，输入后在本地先规范化与去重；新增不立即请求 API，表格展示草稿差异。
- 页面提供统一“保存变更”按钮，提交中禁用编辑；保存时携带 `expectedVersion`。`409` 时保留本地草稿，提示刷新并由管理员决定是否合并。
- 删除与“清空全部”均使用现有确认弹窗；后者为危险操作，需输入确认文本。提供“测试图片 URL”纯文本校验，仅显示解析出的 Host 和允许结果，**不加载图片**。
- 长 Host 截断但可复制或通过 `title` 查看完整值；窄屏表格应允许横向滚动或改为可读列表，避免按钮和文本重叠。

### 5.5 CSP 和部署边界

静态 SPA 的 CSP 不能从数据库动态生成 `img-src` 域名列表。若 CSP 写为 `img-src https:`，它只能限制协议，不能替代应用的精确 Host 校验；若写死图床域名，则每次管理页变更仍需部署配置。

因此本方案以渲染器白名单为主，建议在部署层补充 `img-src 'self' https:` 作为协议级纵深防御，且保持图片 URL 只由受控 Markdown 解析器生成。需要将 CSP 精确限制到动态白名单，或需要隐藏访问者 IP 时，再升级到方案 C 的受控图片代理；代理必须在请求前后执行 SSRF、重定向、IP 地址、大小、类型和缓存治理。

## 6. 修改范围与实施顺序

1. 新增 Prisma 模型与迁移；实现后端模块、DTO、Swagger 和 API 文档。
2. 新增前端 API 封装、领域类型、策略 Provider/Store 与管理页面，注册管理员路由和导航。
3. 将 `useMarkdown` 的图片规则改为 HTTPS + 精确 Host 比较，补齐加载、失败、未授权提示；确保全部复用链路接入。
4. 进行数据迁移前扫描：从现有 Markdown 内容提取图片 Host，生成仅供管理员审核的候选清单，**不自动加入**白名单。
5. 部署后由管理员先配置必要图床，再验证编辑预览、详情和批注预览；最后按实际部署方式添加 CSP 协议级限制。

## 7. 验证与验收

- 解析单测：空策略、加载中、HTTPS 精确匹配、大小写与 URL 规范化、未授权子域、HTTP、`data:`、`javascript:`、IP/localhost、Alt 文本及 URL 含查询参数。
- API 测试：公开读取默认空策略；未认证 `PUT` 返回 `401`；非法 Host 返回 `400`；合法集合规范化去重；空集合；过期版本返回 `409`；并发写入不丢失已确认配置。
- 前端页面：新增、重复、删除、清空、保存中、加载失败、`409`、测试 URL、长域名与移动端布局；确认非管理员看不到导航且直达路由被拦截。
- 集成回归：学习笔记、解决方案、杂谈、模型回答、Prompt 编辑器预览以及 Markdown 批注的详情/预览均只加载允许图片；策略失败或删除 Host 后不产生外部图片请求。
- 运行时网络检查：浏览器 Network 中仅出现白名单域的图片请求，图片请求没有 Referer；检查实际部署 CSP 是否按计划生效。
