# 顶部全局搜索支持摘要与标签方案

## 1. 结论先行

需求可行，且首期不需要修改 Prisma Schema，也不需要引入 Elasticsearch、Meilisearch 等外部搜索服务。

推荐采用“保留现有 `/api/search` 入口，后端改为 PostgreSQL 统一查询，API 返回命中上下文，前端展示命中原因”的方案。搜索范围明确限定为：

- Prompt：名称、描述、标签。
- 解决方案、学习笔记、杂谈、UI 原型、模型回答：标题、摘要、标签。
- 模型回答继续仅对有效管理员会话开放。
- 首期不搜索正文、分类、Prompt 历史版本，也不提供拼写纠错或语义搜索。

与只在现有 Prisma 条件中增加字段相比，推荐方案多了一项 API 返回结构和结果展示改动，但可以解决两个实际问题：

1. 当前不同资源的标签存储方式不一致，Prompt 使用关系表，其他资源使用 PostgreSQL 字符串数组，简单扩展 Prisma 条件会产生不一致的标签匹配语义。
2. 当关键词只命中摘要或标签时，如果结果面板仍只展示标题，用户无法理解该结果为何出现。

## 2. 背景与当前实现

顶部全局搜索的真实调用链为：

`GlobalSearch.tsx` → `globalSearch()` → `GET /api/search` → `SearchService.search()` → Prisma 查询各资源表 → 服务端合并、排序、截取结果。

当前行为如下：

- 前端输入防抖为 `250ms`，默认请求最多 `12` 条结果。
- 后端分别查询 Prompt、解决方案、学习笔记、杂谈、UI 原型；管理员会话额外查询模型回答。
- Prompt 仅匹配 `name`，其他资源仅匹配 `title`。
- 匹配不区分大小写，排序优先级为标题完全匹配、标题前缀匹配、标题包含匹配，相同等级按更新时间倒序。
- API 结果只有 `id`、`title`、`resourceType` 和 `updatedAt`。
- 前端结果只展示标题和资源类型，空状态也明确写着“没有找到标题包含……的内容”。

现有数据已经包含本需求所需字段：

| 资源 | 标题字段 | 摘要等价字段 | 标签存储方式 | 访问范围 |
| --- | --- | --- | --- | --- |
| Prompt | `name` | `description` | `PromptTag` → `Tag.name` 关系 | 公开读取 |
| 解决方案 | `title` | `summary` | `String[]` | 公开读取 |
| 学习笔记 | `title` | `summary` | `String[]` | 公开读取 |
| 杂谈 | `title` | `summary` | `String[]` | 公开读取 |
| UI 原型 | `title` | `summary` | `String[]` | 公开读取 |
| 模型回答 | `title` | `summary` | `String[]` | 仅管理员 |

因此，首期属于搜索查询和结果契约增强，不属于数据库结构建设。

## 3. 目标与约束

### 3.1 目标

- 用户可以通过摘要中的关键词发现标题未包含该词的内容。
- 用户可以通过完整或部分标签名称发现内容，并且英文大小写不影响结果。
- 搜索结果能够明确展示“命中摘要”或“命中标签”，避免结果看起来与关键词无关。
- 保留现有资源跳转、键盘操作、防抖和最多返回数量。
- 保持公开内容与私有模型回答的权限边界。

### 3.2 首期非目标

- 不搜索 Markdown 正文、Prompt 正文或 UI 原型 HTML。
- 不搜索分类、模型名称、来源产品或原始 Prompt。
- 不实现中文分词、同义词、拼写纠错、向量检索或语义搜索。
- 不新增独立搜索服务或缓存中间件。
- 不在本需求中统一改造各资源列表页的局部搜索。

### 3.3 匹配语义

- 输入先执行 `trim`，空白关键词不发起有效搜索。
- 标题、摘要和标签均采用不区分大小写的包含匹配。
- `%`、`_` 和 `\` 按普通字符搜索，后端必须转义 SQL `LIKE` 通配符。
- Prompt 的 `description` 在全局搜索中视为摘要。
- 标签应返回实际命中的完整标签文本，而不是仅返回用户输入片段。

## 4. 候选方案

### 方案 A：最小扩展现有 Prisma 查询

#### 核心思路

保持当前多表并行查询和服务端排序，只在各资源的 `where.OR` 中增加摘要和标签条件。API 响应及前端结果面板保持不变。

#### 优点

- 改动文件和代码量最少。
- 不需要数据库迁移，也不改变 API 返回契约。
- 可以继续沿用当前 Prisma 查询结构。

#### 缺点

- PostgreSQL 标量列表通过 Prisma 搜索时更适合精确匹配，难以同时实现“不区分大小写的标签部分匹配”；Prompt 的关系型标签却可以使用 `contains + insensitive`，不同资源会产生不同语义。
- 只命中摘要或标签的结果仍然只展示标题，用户无法判断命中原因。
- 排序函数当前只基于标题，需要额外补充字段优先级，否则摘要和标签结果会与标题结果混排。
- 后续如果再增加分类或来源字段，条件和排序逻辑会继续分散在多个查询中。

#### 适用场景

只要求快速支持摘要匹配，并且标签仅做大小写敏感的完整值匹配，对结果解释性没有要求的临时版本。

### 方案 B：PostgreSQL 统一查询并返回命中上下文（推荐）

#### 核心思路

保留 `/api/search` 和现有前端调用方式，在 `SearchService` 内使用参数化 SQL 将各资源标准化为相同字段：`id`、`title`、`summary`、`tags`、`resourceType`、`updatedAt`。通过 `UNION ALL` 聚合后统一过滤、计算匹配等级、排序和限制数量。

API 为每条结果增加命中字段与命中文本，例如：

```json
{
  "id": "786da6f1-8c64-4150-af33-382ab105a519",
  "title": "React 状态管理实践",
  "resourceType": "NOTE",
  "updatedAt": "2026-09-20T08:00:00.000Z",
  "matchField": "TAG",
  "matchText": "React"
}
```

前端结果项继续以标题为主信息，并在次要信息区域展示以下内容之一：

- 标题命中：只显示资源类型，避免重复展示标题。
- 标签命中：显示 `标签：React`。
- 摘要命中：显示包含关键词的截断摘要片段。

#### 优点

- 所有资源获得一致的大小写不敏感、部分匹配语义。
- 排序在数据库中统一完成，不需要先对每个资源单独截取再在 Node.js 中合并。
- 用户可以理解摘要或标签命中的原因，搜索体验完整。
- 不需要新增表或外部服务；项目现有 `content-tags` 模块已经使用参数化原生 SQL 处理字符串数组，可复用相同的通配符转义和标签展开思路。
- 后续增加新的搜索字段或资源类型时，可以继续沿用标准化查询结构。

#### 缺点

- SQL 比当前 Prisma `findMany` 更长，需要为每种资源维护字段映射。
- Prompt 标签来自关系表，查询分支需要聚合 `Tag.name`；其他资源直接读取字符串数组，SQL 结构并不完全相同。
- 原生查询结果需要显式定义 TypeScript 类型，并在 Service 中转换为公开 DTO。
- 必须增加针对权限分支、通配符转义和排序规则的验证，不能只依赖静态类型。

#### 适用场景

适合当前项目规模，希望一次把摘要与标签搜索、排序一致性和结果解释性处理完整，同时不引入额外基础设施的场景。

### 方案 C：建立独立搜索索引

#### 核心思路

新增统一的 `search_documents` 表，或使用 PostgreSQL `tsvector`、`pg_trgm` 和 GIN/GiST 索引维护可搜索文本。所有资源写入后同步更新索引，全局搜索只查询索引表。

#### 优点

- 查询路径统一，资源数量和数据量增长后更容易优化。
- 可以继续扩展正文、分类、权重、模糊匹配和高亮片段。
- 主业务表结构差异不会持续扩大全局搜索查询。

#### 缺点

- 需要数据库迁移、索引同步机制和存量数据回填。
- 新建、更新、删除、导入和回滚都必须保证搜索索引一致，增加事务和故障恢复复杂度。
- PostgreSQL 原生全文搜索对中文分词的效果需要额外评估；如果再引入分词扩展或外部引擎，部署成本会继续增加。
- 当前只是新增摘要和标签匹配，建设独立索引与需求规模不相称。

#### 适用场景

适合内容达到较大规模、需要搜索正文、模糊匹配或复杂相关性，并且已经观察到现有查询性能无法满足要求的阶段。

## 5. 横向对比

| 方案 | 实现复杂度 | 性能 | 维护性 | 扩展性 | 实施成本 | 结果解释性 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A. 扩展 Prisma 条件 | 低 | 当前规模可接受；仍是多次查询 | 中；标签语义不统一 | 低至中 | 低 | 低 | 临时、最小改动 |
| B. 统一 SQL + 命中上下文 | 中 | 当前规模良好；单次聚合、统一限制 | 高；查询规则集中 | 中至高 | 中 | 高 | 当前项目的正式实现 |
| C. 独立搜索索引 | 高 | 数据量较大时最好 | 中；需要维护索引一致性 | 高 | 高 | 高 | 正文搜索和大规模数据 |

## 6. 推荐方案与理由

推荐方案 B：PostgreSQL 统一查询并返回命中上下文。

主要理由：

1. 本需求不只是增加两个 `OR` 条件。Prompt 和其他资源的标签结构不同，必须先定义一致的匹配语义。
2. 标题未命中但摘要或标签命中时，前端需要告诉用户命中原因，否则用户会把正确结果误判为搜索错误。
3. 项目所有数据已经位于同一个 PostgreSQL 数据库，使用参数化 `UNION ALL` 查询可以在不引入基础设施的情况下集中完成过滤、排序和限制。
4. 项目已有 `content-tags` 的参数化原生 SQL 实践，能够复用字符串数组展开、大小写归一化和 `LIKE` 通配符转义方式，技术风险可控。
5. 当前没有证据表明需要独立搜索索引。先保持零迁移方案，等真实性能数据达到阈值后再升级，成本更合理。

## 7. 推荐方案详细设计

### 7.1 API 请求

请求保持不变：

```http
GET /api/search?query=react&limit=12
```

`query` 继续限制最大 `120` 个字符，`limit` 继续保持 `1-50`，默认 `12`。不增加前端可控的资源范围或搜索字段参数，避免首期交互复杂化。

### 7.2 API 响应

在 `GlobalSearchItemDto` 和前端 `GlobalSearchItem` 中新增：

```ts
export type GlobalSearchMatchField = 'TITLE' | 'SUMMARY' | 'TAG';

export interface GlobalSearchItem {
  id: string;
  title: string;
  resourceType: GlobalSearchResourceType;
  updatedAt: string;
  matchField: GlobalSearchMatchField;
  matchText?: string;
}
```

约束如下：

- `matchField` 表示该结果最高优先级的命中字段。
- `matchText` 在标签命中时返回完整标签，在摘要命中时返回截断片段。
- 标题命中时可以不返回 `matchText`，避免重复传输标题。
- 摘要片段建议限制在约 `120` 个可见字符，并围绕首个命中位置截取；不得返回完整摘要之外的私有字段。
- 新字段属于响应的增量扩展，旧客户端会忽略额外字段；前后端同版本发布后启用新展示。

### 7.3 后端标准化查询

各资源分支先映射到统一内部结构：

| 资源 | `title` 来源 | `summary` 来源 | `tags` 来源 |
| --- | --- | --- | --- |
| Prompt | `prompts.name` | `prompts.description` | `prompt_tags` 关联 `tags.name` 后聚合 |
| 解决方案 | `solutions.title` | `solutions.summary` | `solutions.tags` |
| 学习笔记 | `notes.title` | `notes.summary` | `notes.tags` |
| 杂谈 | `miscellanies.title` | `miscellanies.summary` | `miscellanies.tags` |
| UI 原型 | `ui_prototypes.title` | `ui_prototypes.summary` | `ui_prototypes.tags` |
| 模型回答 | `model_responses.title` | `model_responses.summary` | `model_responses.tags` |

查询实现约束：

- 使用 `Prisma.sql` 插值参数，不拼接用户输入形成 SQL。
- 对 `%`、`_`、`\` 做转义，并使用显式 `ESCAPE '\'`。
- 标签通过 `unnest(tags)` 匹配；Prompt 标签通过关系表聚合后采用同样规则。
- 公开查询不能包含模型回答分支；只有 `AuthService.getSession(request)` 返回有效管理员会话后，才将模型回答 SQL 片段加入查询。
- 原生查询的内部行结构必须使用明确的 TypeScript `interface`，不得使用 `any`。
- DTO 只返回结果展示需要的字段，不返回内部排名、完整标签数组或完整摘要。

### 7.4 相关性排序

推荐排序等级如下：

1. 标题完全匹配。
2. 标题前缀匹配。
3. 标题包含匹配。
4. 标签完全匹配。
5. 标签前缀匹配。
6. 标签包含匹配。
7. 摘要包含匹配。
8. 相同匹配等级按 `updatedAt` 倒序。
9. 时间相同时按 `resourceType`、`id` 提供稳定排序。

这样可以保持当前“标题优先”的用户预期，同时让标签比摘要获得更高权重。某条内容命中多个字段时，只使用最高优先级命中决定 `matchField` 和排序，但不会生成重复结果。

### 7.5 前端结果展示

保留当前下拉面板、方向键切换、Enter 打开、Escape 关闭和路由跳转行为。

结果项调整为：

- 第一行：标题。
- 第二行：资源类型；摘要或标签命中时追加分隔符和命中上下文。
- 标签命中示例：`学习笔记 · 标签：React`。
- 摘要命中示例：`解决方案 · ……通过 AbortController 取消旧请求……`。
- 摘要片段中的关键词可以使用 `<mark>` 或等价样式高亮，但必须由 React 文本节点渲染，不使用 `dangerouslySetInnerHTML`。

同步修改文案：

- 占位文案建议改为“搜索标题、摘要或标签”。
- 空状态改为“没有找到包含‘关键词’的内容”。
- 加载文案可以继续使用“正在搜索所有内容……”。

由于结果项会增加一行上下文，应保持面板最大高度和内部滚动，避免摘要片段把下拉面板无限撑高。

### 7.6 权限与数据边界

- Prompt、解决方案、学习笔记、杂谈和 UI 原型继续允许访客搜索。
- 模型回答只有管理员会话可以参与查询和返回。
- 不能先查询模型回答再在应用层过滤，否则查询耗时、错误或统计信息可能形成不必要的私有资源侧信号。
- 标签和摘要均可能包含敏感文本，因此模型回答的 `matchText` 必须受到与标题相同的会话边界保护。
- 搜索接口继续只返回详情页可公开读取的资源，不新增批注、历史版本或未公开字段。

### 7.7 性能策略

首期不新增索引，理由是当前标题搜索本身使用 `%keyword%` 包含匹配，普通 B-tree 标题索引不能直接优化该模式；新增摘要和标签后应先测量真实数据规模与响应时间。

建议采用以下演进阈值：

- 先在代表性数据上记录 `/api/search` 的 p50、p95 和最慢查询计划。
- 如果 p95 持续超过 `200ms`，或单个公开资源表达到数万级记录，再单独评估 `pg_trgm`、GIN 索引或统一搜索索引表。
- 性能优化必须以 `EXPLAIN (ANALYZE, BUFFERS)` 证据为基础，不因字段增加直接引入外部搜索服务。
- 保留前端 `250ms` 防抖和服务端最大 `50` 条限制；默认仍返回 `12` 条。

## 8. 预计影响范围

后续实施时预计涉及：

- `apps/api/src/search/search.service.ts`：统一查询、权限分支、排名和命中片段。
- `apps/api/src/search/dto/global-search-response.dto.ts`：命中字段 DTO 与 Swagger。
- `apps/web/src/types/domain.ts`：前端搜索结果类型。
- `apps/web/src/components/layout/GlobalSearch.tsx`：结果上下文、文案和关键词高亮。
- `apps/web/src/assets/main.css`：上下文省略、高亮和结果项高度控制。
- `docs/api/search.md`：搜索范围、排序和响应字段。
- `docs/features/content-discovery/README.md`：当前行为与限制。

首期不涉及：

- `apps/api/prisma/schema.prisma`。
- Prisma 迁移。
- 各资源详情、编辑、列表 API。
- 外部依赖或新的 UI 组件库。

## 9. 风险与缓解措施

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 原生 SQL 字段或表名维护错误 | 某一资源搜索缺失 | 为每个资源类型建立独立命中用例，统一内部行类型 |
| `%`、`_` 被当作通配符 | 返回范围超出用户预期 | 复用并测试现有 `escapeLikePattern` 逻辑 |
| Prompt 标签和数组标签行为不一致 | 同一关键词在不同资源表现不同 | 统一使用 `lower + contains` 语义，返回实际标签文本 |
| 摘要命中但前端不解释 | 用户误以为结果错误 | API 返回 `matchField`、`matchText`，前端展示上下文 |
| 模型回答摘要或标签泄露 | 私有数据泄露 | 未认证查询完全不拼接模型回答分支，并覆盖访客用例 |
| 结果项高度增加 | 下拉面板可扫描性下降 | 上下文单行省略、限制面板高度、保持内部滚动 |
| 包含匹配在数据增长后变慢 | 搜索延迟升高 | 记录性能基线，达到阈值后再引入 trigram 或搜索索引 |

## 10. 验收标准

### 10.1 功能用例

- 关键词只出现在标题时，可以检索到并标记为 `TITLE`。
- 关键词只出现在 Prompt `description` 或其他资源 `summary` 时，可以检索到并显示摘要片段。
- 关键词只出现在标签时，可以检索到并显示完整标签。
- 英文标签使用不同大小写和标签片段仍能命中。
- 包含 `%`、`_`、`\` 的关键词按普通字符处理。
- 一条资源同时命中标题、摘要和标签时只返回一次，并采用标题排名。
- 超过 `limit` 时结果数量正确，排序稳定。

### 10.2 权限用例

- 访客搜索模型回答独有的标题、摘要或标签时均不返回模型回答。
- 管理员使用相同关键词可以返回模型回答，并正确跳转详情页。
- 管理员会话失效后再次搜索，不保留之前查询的模型回答结果。

### 10.3 交互用例

- 连续输入时旧请求结果不会覆盖新关键词结果。
- 方向键、Enter、Escape、点击外部关闭行为保持不变。
- 标题、摘要和标签命中均具有可理解的展示文案。
- 空状态不再声称只搜索标题。
- 长标题、长摘要、长标签不会撑破结果面板。

### 10.4 验证边界

- 实施后应执行非构建类静态检查、类型检查和 `git diff --check`；是否执行构建必须遵守项目授权规则。
- API 的大小写、通配符、排序和权限必须通过真实 PostgreSQL 数据验证，不能只依据 TypeScript 静态检查。
- 前端键盘和面板滚动需要浏览器运行时验证，API 请求成功不等于交互已验证。

## 11. 分阶段落地建议

### 第一阶段：完成正式可用能力

- 实现标题、摘要、标签统一查询。
- 增加命中字段和命中文本。
- 更新结果面板、空状态和 API 文档。
- 完成公开资源与模型回答权限回归。

### 第二阶段：基于数据决定是否优化

- 收集查询耗时和查询计划。
- 仅当性能阈值被触发时增加 `pg_trgm` 或搜索索引。
- 只有在产品明确要求后，再评估正文搜索、分类搜索、拼写纠错或语义搜索。

本方案当前只用于需求评估和后续实施依据，不包含业务代码改动。
