## Context

前端当前通过 Zustand `useConfirmStore` 暴露一个返回 `Promise<boolean>` 的全局确认能力，并由 `AppLayout` 中唯一的 `ConfirmDialog` 渲染确认弹窗。Prompt 版本回滚和所有删除操作共用该能力，但删除调用只通过 `destructive: true` 改变按钮样式，没有更强的防误触机制。

用户可见的删除对象包括 Prompt、解决方案、学习笔记、UI 原型、分类、标签和批注。前六类对象具有适合识别目标的名称或标题；批注没有短且稳定的名称，其关联原文可能包含换行、Markdown 或代码，正文也可能很长。解决方案和学习笔记删除时还会由 Prisma 关系级联删除批注，Prompt 删除时会级联删除历史版本和标签关联。

该能力是跨页面的前端交互变更。项目继续使用本地 UI 组件、Tailwind CSS、Zustand 和现有 API，不增加依赖，不修改数据库或后端接口。

## Goals / Non-Goals

**Goals:**

- 所有用户可见的删除操作在发起 DELETE 请求前都必须完成输入确认。
- 使用资源名称或标题帮助用户确认具体目标；批注使用固定、易输入的确认短语。
- 将输入确认能力集中在全局确认基础设施中，并为删除操作提供统一调用入口。
- 保持现有普通确认调用兼容，使 Prompt 版本回滚等操作不出现输入框。
- 准确展示不可恢复和级联影响，并补齐输入状态、键盘操作和基本弹窗语义。

**Non-Goals:**

- 不把输入确认作为权限控制、安全认证或防止直接 API 调用的措施。
- 不修改 DELETE API 的请求体、请求头、响应或后端校验逻辑。
- 不新增软删除、回收站、数据恢复、审计日志或批量删除能力。
- 不重构所有弹窗为新的第三方 Dialog 组件，也不引入新的 UI 框架。

## Decisions

### 1. 扩展通用确认契约，并提供专用删除确认入口

在通用 `ConfirmOptions` 中增加可选的 verification 配置，包含必须匹配的 `expectedText` 和可选说明文本。`ConfirmDialog` 仅在存在 verification 时渲染输入确认区域。

`useConfirm` 同时提供 `confirmDeletion` 封装。该封装强制调用方提供 `expectedText`，并统一设置危险样式和“确认删除”按钮文本；现有 `confirm` 保持原有行为。所有删除入口改用 `confirmDeletion`，普通确认继续调用 `confirm`。

选择该方案而不是在各页面维护本地输入弹窗，是因为全局契约可以统一交互和校验，并降低新增删除入口遗漏规则的概率。仅在 `confirm` 上增加可选字段但不提供专用入口虽然改动更少，却无法从调用语义上区分删除与普通确认。

### 2. 资源使用名称或标题，批注使用固定短语

确认文本映射如下：

| 对象 | 确认文本 |
| --- | --- |
| Prompt | `prompt.name` |
| 解决方案 | `solution.title` |
| 学习笔记 | `note.title` |
| UI 原型 | `prototype.title` |
| 分类 | `category.name` |
| 标签 | `tag.name` |
| 批注 | 固定文本 `删除批注` |

批注弹窗继续展示截断后的关联原文用于识别目标，但不要求输入该原文。要求输入关联原文会因长度、换行和代码字符造成明显的可用性问题；要求输入所属解决方案或笔记标题又不能准确识别具体批注。

### 3. 使用可见文本精确匹配，并容忍首尾空白

校验时对输入值和期望值执行 Unicode NFC 规范化和首尾空白移除，然后进行区分大小写的严格相等比较。内部空白、标点和字符必须一致，不转换大小写。

该规则保留 GitHub 风格的目标识别强度，同时避免输入法产生的等价 Unicode 序列或历史导入数据中的不可见首尾空白导致无法确认。弹窗展示同样经过首尾空白移除的期望文本，允许用户复制粘贴，不阻止粘贴行为。

### 4. 输入状态由确认弹窗管理，每次会话独立重置

verification 定义保存在全局确认状态中，用户当前输入保存在 `ConfirmDialog` 本地状态。弹窗打开、期望文本变化、取消或完成确认时都重置输入，避免上一次确认文本泄漏到下一次操作。

输入框自动聚焦；只有匹配成功时危险按钮才可用；Enter 只在匹配成功时提交；Escape 等同取消。弹窗补充 `role="dialog"`、`aria-modal="true"`、标题关联和输入 label，使输入确认具备基本键盘与辅助技术语义。

确认 Promise 仍只负责收集用户意图，匹配后弹窗关闭，再由现有页面函数调用 DELETE API。这样无需把各资源的异步删除和错误处理耦合进全局弹窗。

### 5. 删除影响由调用方明确传入

确认弹窗保持通用，不根据资源类型推导业务影响。各删除入口通过 description 明确传入实际结果：

- Prompt：同时删除历史版本及标签关联。
- 解决方案、学习笔记：同时删除全部批注。
- 分类：相关 Prompt 变为未分类。
- 标签：Prompt 与该标签的关联被删除。
- UI 原型：资源本身不可恢复。
- 批注：批注不可恢复，但 Markdown 原文不变。

由调用方负责业务文案，可以让提示与真实页面上下文和后端关系保持一致，避免全局组件依赖领域类型。

## Risks / Trade-offs

- [所有删除都要求输入会增加分类、标签和批注等小对象的操作成本] → 删除属于低频且不可恢复操作，优先保持一致的防误触规则；批注使用固定短语降低额外负担。
- [标题最长可达 200 个字符，完整输入较费时] → 清晰展示并允许复制期望文本，不限制粘贴；弹窗内容允许换行且保持可读。
- [未来新增删除入口可能继续直接调用通用 `confirm`] → 提供命名明确的 `confirmDeletion`，并在验证阶段静态搜索所有 DELETE 调用和删除处理函数。
- [前端校验可被绕过] → 该能力明确只防止 UI 误操作；权限和 API 安全继续由既有后端边界负责。
- [修改全局弹窗可能影响版本回滚等普通确认] → verification 保持可选，并验证无 verification 时界面和 Promise 行为与现状一致。

## Migration Plan

1. 以向后兼容方式扩展确认状态和弹窗，先保留现有 `confirm` 调用可用。
2. 增加 `confirmDeletion`，逐一迁移所有删除入口并更新影响文案。
3. 静态检查所有用户可见 DELETE 调用均已接入输入确认，并验证普通回滚确认未出现输入框。
4. 该变更不涉及数据迁移或部署顺序。需要回滚时仅回退前端确认基础设施和调用方改动，后端无需处理。
